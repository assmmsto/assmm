الطلبات الجديدة تُفقد صامتة — الأدمن لا يرى أي طلب جديد db.js:123 · app.js:919 · جدول orders

طبقة البيانات ORDER_COLS تتضمّن عموداً اسمه payerEmail، وapp.js يضعه في كل طلب — حتى إن كان فارغاً (نص فارغ لا يعني «غائب»). لكن هذا العمود غير موجود أصلاً في جدول orders.

وPostgREST يرفض الإدراج بالكامل لو وُجد حقل واحد غير معروف. النتيجة: الطلب يُحفظ في متصفح المشتري فقط، والمشتري يرى «تم إرسال طلبك» — بينما الأدمن لا يرى شيئاً على الإطلاق. المشتري يدفع، والأدمن لا يعلم.

لماذا لم يكتشفه أحد؟ لأن الكود «يسقط بأمان» إلى التخزين المحلي — لا رسالة خطأ للمشتري ولا للأدمن. الطلب الحقيقي الوحيد في القاعدة (REF-MUD7EDEA) أُنشئ قبل إضافة هذا الحقل، لذلك بدا كل شيء سليماً.

ثغرة متبقية في إصلاح الأمان الجاهز — الطلبات تبقى مقروءة للجميع supabase-security-fix.sql:145-149

لاحظتُ في ملف الإصلاح أن سياسة قراءة الطلبات هي using (true)، مع تعليق يقول إن المرجع «صار غير قابل للتخمين». لكن using(true) تعني كل الصفوف — والمرجع غير القابل للتخمين لا يحميك إن كنت تستطيع سرد الجدول كله.

-- بعد تشغيل الإصلاح كما هو: GET /rest/v1/orders?select=* → 200 كل الطلبات، مع أسماء المشترين وإثباتات الدفع

أي أن أحد بنود فحصك الخاص («قراءة كل بيانات المشترين») سيبقى فاشلاً بعد الإصلاح.

✓ الإصلاح — استبدل السياسة بدالة

اسحب صلاحية القراءة الجماعية، واسمح فقط بجلب طلب واحد بمرجعه عبر دالة مُعرَّفة بأمان. أضف هذا في نهاية ملف الإصلاح:

-- اسمح بالبحث عن طلب واحد فقط، بلا سرد الجدول drop policy if exists "orders: قراءة بمتابعة الطلب" on orders; revoke select on orders from anon, authenticated; create or replace function get_order_by_reference(ref text) returns table (reference text, "productName" text, total numeric, currency text, status text, "licenseKey" text, "createdAt" text) language sql security definer set search_path = public as $$ select o.reference, o."productName", o.total, o.currency, o.status, o."licenseKey", o."createdAt"::text from orders o where o.reference = ref limit 1; $$; grant execute on function get_order_by_reference(text) to anon, authenticated;

ثم عدّل db.js → getOrder() ليستدعي client.rpc('get_order_by_reference', { ref }) بدل .from('orders').select(). صندوق «متابعة الطلب» سيعمل كما هو.

٦ خطة العمل — بالترتيب

المرحلة 1 — قبل النشر · إلزامية

~45 دقيقة
  1. شغّل supabase-security-fix.sql في Supabase → SQL Editor. هذا وحده يحلّ المانع الأول ويغلق المانع الثاني جزئياً.
  2. احذف licenseKeys و usedKeys من data/products.json. يحلّ النصف الثاني من تسريب المفاتيح.
  3. احذف رابط «لوحة الأدمن» من فوتر index.html (السطر 206). يغلق المانع الثالث فوراً.
  4. أضف دالة get_order_by_reference (القسم ٣ أعلاه) وأغلق قراءة الطلبات الجماعية.
  5. تعطّل كل وسيلة دفع لا تملكها فعلاً — وتبقّي واحدة حقيقية.
  6. شغّل python tools/build-dist.py وتأكد أنه قال «🎉 جاهز للنشر».
  7. انشر مجلد dist/ بالسحب والإفلات على Cloudflare Pages.
  8. افتح الموقع وجرّب بنفسك: أنشئ طلباً وهمياً ثم تأكد أنك تراه في لوحة Supabase. هذا الفحص يكشف أي مانع مشابه في المستقبل.

المرحلة 2 — أول أسبوع · تجعل المتجر يعمل فعلاً

~ساعتان
  1. املأ روابط التسليم السبعة من لوحة الأدمن — بلا هذا لا يوجد بيع فعلي.
  2. صحّح أرقام التحميلات إلى صفر، واحذف «50+ مطوّر»، وأزل ادّعاءات E2EE وCI/CD.
  3. حدّث الصفحات القانونية: صحّح §3 من الخصوصية، واستبدل البريد الحقيقي.
  4. أنشئ مهمة cron كل 3 أيام لمنع إيقاف Supabase المجاني.
  5. احصل على نطاق (Cloudflare Registrar ≈ 10$/سنة) — أو ابدأ بـ اسم-المشروع.pages.dev واستبدل example.com به مؤقتاً في 9 مواضع.

المرحلة 3 — لاحقاً · يحوّله من تجربة إلى مشروع

عند الحاجة
  1. Supabase Auth لحساب الأدمن — البوابة المحلية الحالية ليست مصادقة. حساب واحد ببريد وكلمة مرور، ثم سياسات للمستخدم الموثّق. هذا ما يجعل اللوحة آمنة فعلاً (القالب جاهز كتعليق في نهاية ملف الإصلاح).
  2. حدّ معدّل للطلبات — حالياً أي زائر يستطيع إغراق جدول الطلبات. حل بسيط: قيد في سياسة الإدراج + مرجع فريد (المرجع العشوائي موجود فعلاً).
  3. صور منتجات حقيقية — أكبر تحسين مبيعي متبقٍ، وأرخصه.
  4. رفع رقم الإصدار إلى v17 مع أي تعديل على CSS/JS — وتذكّر: index.html + admin.html + sw.js + الصفحات القانونية معاً.
